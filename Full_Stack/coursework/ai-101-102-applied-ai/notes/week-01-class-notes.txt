You’re actually in a really good position for an analytics-focused SQL class, because you already know the “database mechanics” side of SQL. What changes now is the purpose.
In database/admin-oriented SQL, the question is usually: How do I store, retrieve, update, and organize data correctly?
In analytics SQL, the question becomes: How do I turn raw rows into an answer to a business question?
That distinction is the core of the class.
You already know things like SELECT, INSERT, joins, tables, database structure, and probably some filtering. So I would not spend much time relearning basic syntax. Instead, you should focus on becoming very strong at aggregation, grouping, conditional logic, window functions, date logic, CTEs, subqueries, and translating vague questions into precise SQL.
Here is the mental model I want you to use all semester:
Raw data → define the grain → filter → combine → calculate → summarize → compare → explain
That is analytics SQL.
Suppose you have a table like:
sales
-----
order_id
customer_id
order_date
product_id
quantity
revenue

Basic SQL asks:
SELECT *
FROM sales;
Analytics SQL asks:
SELECT

    SUM(revenue) AS total_revenue,
    AVG(revenue) AS avg_order_revenue,
    COUNT(DISTINCT customer_id) AS customers
FROM sales
WHERE order_date >= '2026-01-01'
GROUP BY region
ORDER BY total_revenue DESC;
Now you’re not retrieving records. You’re answering:
Which regions generated the most revenue, and how many customers contributed to it?
That is the shift you want to master.
1. The most important concept: grain
If I could make you master only one thing before your first exam, it would be grain.
The grain means:
What does one row represent?
For example, one row might represent:
one customer
one transaction
one product
one transaction line item
one customer per month
one store per day
This matters constantly.
Imagine these tables:
orders
order_id
customer_id
order_date
order_items
order_id
product_id
quantity
price
orders has one row per order.
order_items has one row per product within an order.
If you join them:
SELECT *
FROM orders o
JOIN order_items oi
    ON o.order_id = oi.order_id;
You have changed the grain.
Now your result is approximately:
one row per order-item combination
That means if an order contains five products, the order appears five times.
This becomes extremely important when you calculate things.
For example, this could be wrong:
SELECT
    COUNT(order_id)
FROM orders o
JOIN order_items oi
    ON o.order_id = oi.order_id;
That counts line items, not orders.
You may need:
COUNT(DISTINCT o.order_id)
instead.
A lot of analytics SQL mistakes are actually grain mistakes disguised as SQL mistakes.
Whenever you write a query, ask yourself:
What does one row represent before the join?
and then:
What does one row represent after the join?
If you consistently do that, you will already be ahead of a lot of students.
2. Aggregations are now much more important
You probably already know:
SUM()
AVG()
COUNT()
MIN()
MAX()
But analytics depends heavily on understanding exactly what those functions are doing.
For example:
SELECT
    SUM(revenue)
FROM sales;
answers:
What is total revenue?
But:
SELECT
    region,
    SUM(revenue)
FROM sales
GROUP BY region;
answers:
What is total revenue for each region?
Think of GROUP BY as saying:
Collapse the dataset into one row for each unique combination of these columns.
Example:
SELECT
    region,
    product_id,
    SUM(revenue) AS revenue
FROM sales
GROUP BY
    region,
    product_id;
The grain of the result is now:
one row per region-product combination
That way of thinking will make GROUP BY much easier.
3. Know the difference between WHERE and HAVING
This is a classic exam topic.
WHERE filters rows before aggregation.
HAVING filters groups after aggregation.
Suppose you want regions with more than $100,000 in revenue.
Wrong:
SELECT
    region,
    SUM(revenue)
FROM sales
WHERE SUM(revenue) > 100000
GROUP BY region;
Correct:
SELECT
    region,
    SUM(revenue) AS total_revenue
FROM sales
GROUP BY region
HAVING SUM(revenue) > 100000;
A useful mental model is:
FROM
JOIN
WHERE
GROUP BY
HAVING
SELECT
ORDER BY
LIMIT
That is roughly the logical order SQL processes the query.
That explains a lot of behavior.
4. CASE statements are huge in analytics
You should become very comfortable with:
CASE
    WHEN condition THEN value
    WHEN condition THEN value
    ELSE value
END
Example:
SELECT
    customer_id,
    revenue,
    CASE
        WHEN revenue >= 1000 THEN 'High Value'
        WHEN revenue >= 500 THEN 'Medium Value'
        ELSE 'Low Value'
    END AS customer_segment
FROM sales;
But the more powerful analytics use is conditional aggregation.
Example:
SELECT
    region,
    SUM(
        CASE
            WHEN product_category = 'Electronics'
            THEN revenue
            ELSE 0
        END
    ) AS electronics_revenue
FROM sales
GROUP BY region;
You are basically saying:
Add revenue only when the row matches this condition.
Conditional aggregation is one of the most useful techniques you can learn.
You can calculate several metrics in one query:
SELECT
    region,
    SUM(revenue) AS total_revenue,
    SUM(
        CASE
            WHEN product_category = 'Electronics'
            THEN revenue
            ELSE 0
        END
    ) AS electronics_revenue,
    SUM(
        CASE
            WHEN product_category = 'Furniture'
            THEN revenue
            ELSE 0
        END
    ) AS furniture_revenue
FROM sales
GROUP BY region;
That kind of query shows up constantly in business analytics.
5. Window functions are probably the biggest new skill
Depending on how advanced your class is, window functions may become one of the most important topics.
A window function lets you calculate something across multiple rows without collapsing the rows like GROUP BY does.
This distinction matters enormously.
Imagine:
employee | department | salary
John     | Sales      | 70000
Mary     | Sales      | 80000
Sara     | Sales      | 90000
Alex     | IT         | 95000
Mike     | IT         | 100000
With GROUP BY:
SELECT
    department,
    AVG(salary)
FROM employees
GROUP BY department;
you get:
Sales | 80000
IT    | 97500
The individual employees disappear.
But with:
SELECT
    employee,
    department,
    salary,
    AVG(salary) OVER (
        PARTITION BY department
    ) AS department_avg
FROM employees;
you get:
John  | Sales | 70000  | 80000
Mary  | Sales | 80000  | 80000
Sara  | Sales | 90000  | 80000
Alex  | IT    | 95000  | 97500
Mike  | IT    | 100000 | 97500
That lets you compare each row to the group.
For example:
salary -
AVG(salary) OVER (
    PARTITION BY department
)
tells you how far each employee is above or below the department average.
That is very analytics-oriented.

7. Top N per group
This is a classic analytics problem.
Question:
Find the top three products by revenue within every category.
You cannot easily solve that with a simple GROUP BY.
A common solution:
WITH product_revenue AS (
    SELECT
        category,
        product_id,
        SUM(revenue) AS revenue
    FROM sales
    GROUP BY
        category,
        product_id
),
ranked_products AS (
    SELECT
        category,
        product_id,
        revenue,
        RANK() OVER (
            PARTITION BY category
            ORDER BY revenue DESC
        ) AS rank_num
    FROM product_revenue
)
SELECT *
FROM ranked_products
WHERE rank_num <= 3;
This query combines several important analytics skills:
aggregation
CTEs
window functions
filtering
ranking
If you can understand queries like this comfortably, you're moving toward A-level competence.
8. CTEs will make difficult queries much easier
A CTE uses:
WITH name AS (
    SELECT ...
)
Example:
WITH customer_sales AS (
    SELECT
        customer_id,
        SUM(revenue) AS total_revenue
    FROM sales
    GROUP BY customer_id
)
SELECT *
FROM customer_sales
WHERE total_revenue > 5000;
You could sometimes accomplish the same thing with a subquery:
SELECT *
FROM (
    SELECT
        customer_id,
        SUM(revenue) AS total_revenue
    FROM sales
    GROUP BY customer_id
) x
WHERE total_revenue > 5000;
But CTEs tend to be much easier to read.
Think of them as creating temporary intermediate datasets.
I strongly recommend solving analytics problems in steps.
Instead of trying to write one giant query, think:
Step 1:
Calculate customer revenue.
Step 2:
Rank customers.
Step 3:
Filter top customers.
Then write:
WITH customer_revenue AS (...),

That is much easier to debug.

10. Running totals
Suppose monthly revenue is:
January   10000
February  12000
March     8000
A running total would be:
January   10000
February  22000
March     30000
You can calculate that using:
SUM(revenue) OVER (
    ORDER BY month
)
Example:
SELECT
    month,
    revenue,
    SUM(revenue) OVER (
        ORDER BY month
    ) AS cumulative_revenue
FROM monthly_sales;
Window functions like this are extremely common in analytics.
11. LAG and LEAD
These functions let you compare rows over time.
Suppose you have:
month | revenue
Jan   | 10000
Feb   | 12000
Mar   | 15000
You could write:
SELECT
    month,
    revenue,
    LAG(revenue) OVER (
        ORDER BY month
    ) AS previous_month_revenue
FROM monthly_sales;
Now:
Jan | 10000 | NULL
Feb | 12000 | 10000
Mar | 15000 | 12000
Then you can calculate month-over-month growth:
(revenue - previous_revenue)
/
previous_revenue
Often you'll use a CTE:
WITH revenue_with_previous AS (
    SELECT
        month,
        revenue,
        LAG(revenue) OVER (
            ORDER BY month
        ) AS previous_revenue
    FROM monthly_sales
)
SELECT
    month,
    revenue,
    previous_revenue,
    (revenue - previous_revenue)
    / previous_revenue AS growth_rate
FROM revenue_with_previous;
That is very typical analyst work.

13. Watch out for duplicate multiplication
One of the biggest real-world analytics problems happens when you join multiple one-to-many tables.
Imagine:
customers
orders
support_tickets
A customer has:
3 orders
2 support tickets
If you join all three directly:
customers
JOIN orders
JOIN support_tickets
you might get:
3 × 2 = 6 rows
for that customer.
That can accidentally inflate your totals.
The safer strategy is often:
WITH order_summary AS (
    SELECT
        customer_id,
        COUNT(*) AS orders
    FROM orders
    GROUP BY customer_id
),
ticket_summary AS (
    SELECT
        customer_id,

14. NULLs matter more than people realize
You want to understand:
NULL
does not mean:
0
and does not mean:
''
NULL represents missing or unknown data.
Therefore:
column = NULL
doesn't work correctly.
Use:
column IS NULL
or:
column IS NOT NULL
You'll also use:
COALESCE()
Example:
COALESCE(discount, 0)
meaning:
If discount is NULL, use 0.
Example:
revenue - COALESCE(discount, 0)
Without COALESCE, a NULL discount might cause the whole expression to become NULL.
15. COUNT(*) vs COUNT(column)
This is another common test question.
Suppose:

1           | 555...
2           | NULL
3           | 555...
Then:

returns:

while:
COUNT(phone)
returns:
2
because COUNT(column) ignores NULLs.
And:

counts unique customers.
You want those distinctions completely automatic in your head.
16. Ratios and percentages
Analytics involves tons of percentages.
For example:
What percentage of revenue comes from each region?
You could use:
SELECT
    region,
    SUM(revenue) AS region_revenue,
    SUM(revenue)
    /
    SUM(SUM(revenue)) OVER () AS revenue_share
FROM sales
GROUP BY region;
That second expression is worth studying.
The inner:
SUM(revenue)
calculates revenue per region.
Then:
SUM(...) OVER ()
calculates the total across all regions.
So you're doing:
region revenue / company revenue
That's an extremely analytical use of SQL.

        total_spent,
        CASE
            WHEN total_spent >= 5000 THEN 'VIP'
            WHEN total_spent >= 1000 THEN 'Regular'
            ELSE 'Low Spend'
        END AS segment
    FROM customer_sales
)
SELECT
    segment,
    COUNT(*) AS customers,
    AVG(total_spent) AS avg_spending
FROM customer_segments
GROUP BY segment;
That's the kind of SQL you'll use in real analytics work.
Eventually get good at window functions. These are where SQL starts becoming extremely powerful.
For example, suppose you want to rank customers:
SELECT
    customer_id,
    total_spent,
    RANK() OVER (
        ORDER BY total_spent DESC
    ) AS spending_rank
FROM customer_sales;
Or compare a row to a previous month:
LAG(revenue) OVER (
    ORDER BY month
)
Common ones worth learning are:
ROW_NUMBER()
RANK()
DENSE_RANK()
LAG()
LEAD()
SUM() OVER()
AVG() OVER()
Don't worry if those seem weird initially. Window functions feel strange until they suddenly click.
The best practice method
I wouldn't spend most of your study time watching SQL tutorials.
Instead, spend roughly:
20% learning → 80% writing SQL
Take a small database and give yourself questions.
For example:

Then answer increasingly difficult questions:
How many customers are there?
Which five products cost the most?
How many customers live in each state?

What is revenue by month?

Which product generated the most revenue?
Which customers haven't ordered anything?
What percentage of revenue came from each category?

Which customers increased their spending from last month?
That progression takes you from beginner SQL to legitimately useful analytics SQL.
One habit that will dramatically improve your SQL
Before typing anything, write the problem in plain English.
For example:
Find the top 10 customers by total spending in 2026.
Then translate it:
Need:
customer
total spending
Tables:
customers
orders
Relationship:
customers.customer_id = orders.customer_id
Filter:
orders from 2026
Aggregation:
SUM(amount)
Group:
customer
Sort:
total spending DESC
Limit:
10
Then write the SQL.
SELECT
    c.customer_id,
    c.name,
    SUM(o.amount) AS total_spent
FROM customers c
JOIN orders o
    ON c.customer_id = o.customer_id
WHERE o.order_date >= '2026-01-01'
  AND o.order_date < '2027-01-01'
GROUP BY
    c.customer_id,
    c.name
ORDER BY total_spent DESC
LIMIT 10;
That method prevents a ton of mistakes.
Also learn SQL's logical execution order
This is extremely useful because SQL isn't logically processed in the same order you type it.
You write:

But conceptually SQL works more like:

WHERE

GROUP BY
↓

↓

↓

Once you understand that, things like "why can't I use this alias here?" start making much more sense.
